## 2. 层级链：五层容器 + 两条业务轴

### 2.1 容器链（D2）

```text
Tenant              签约 / 计费 / 配额 / 数据隔离的唯一边界
└── Organization    成员 / 角色 / 权限的边界（子公司、部门、事业部）
    └── Product     产品——需求与功能资产的家（长期，永不归档）
        ├── ═══ 产品轴 ═══  Requirement / Feature / FP / RP / Screen / Resource
        └── Workspace       项目分组容器（团队 / 环境 / 客户 / 业务线）
            └── Project     ═══ 交付轴 ═══  一次有始有终的交付
                └── Task
```

### 2.2 每一层的唯一职责

一层只做一件事，职责不重叠——这是判断"某个字段该放哪层"的唯一依据。

| 层 | 唯一职责 | 归属于它的对象 |
|---|---|---|
| **Tenant** | 钱与量 | 订阅、账单、配额、Token 池、用量统计、数据驻留地域 |
| **Organization** | 人与权 | 成员、角色、权限策略、审计日志、Secret |
| **Product** | 产品是什么 | Requirement、Feature、FP、RP、Screen、Resource、术语库、生产率基线 |
| **Workspace** | 一组项目共享什么 | AI Runtime、Git Repo 绑定、Agent 配置、环境变量、Skill 集合 |
| **Project** | 这一轮做什么 | Task、Bug、Release、TestRun、认领的 FP 范围 |

Workspace 这一层最容易被写空。它的实质价值在于：**Runtime 和 Repo 绑定在 Workspace 上**，
一组项目共用一台 Hermes 和同一套仓库配置——这正好落实文档⑧ 的「1 Workspace = 1 独立 Hermes EC2」。

### 2.3 双轴仍然成立，分叉点是 Product

```text
                              Tenant
                                │
                          Organization
                                │
                             Product
                    ┌───────────┴───────────┐
                    │                       │
            ═══ 产品轴 ═══            ═══ 交付轴 ═══
         （长期累积 / 跨项目复用）      （临时 / 有始有终）
                    │                       │
            Requirement (REQ)           Workspace
                    │                       │  ├── AI Runtime
              PRD Document                  │  └── Git Repo
                    │                       │
             Feature (FE)                Project
                    │                       │
        ★ Function Point (FP) ◄══ N:M ══════┤
                    │                       ├── Task ── Execution ── Step
           Rule Point (RP)                  ├── Bug
                    │                       └── Release
              TestCase ◄═══ 引用 ═══════════════ TestRun
                    │
        Screen ── Resource ── Translation
```

**FP 是两轴唯一的连接点。**

```text
Project 的范围 = 它认领的一组 FP
Project 的进度 = Σ(已完成 FP 权重) / Σ(认领 FP 权重)
```

这同时解决了文档⑨ 抱怨的"132/200 Tasks = 66% 不准"——进度本来就不该按 Task 数算。

## 3. 五层的代价与必须的配套设计

五层容器有一个真实的冲突需要正面处理：**文档⑨ 明确反对**让用户先建一串容器才能用。

> 不要强迫第一次访问用户先：Create Organization → Create Workspace → Create Project → Configure Permission → …
> 这会增加首次使用门槛。

### 3.1 解法：层级自动创建，用户只感知 Project

注册和首次使用时，后端**静默创建**完整的四层容器，用户界面上只出现 Project：

```text
用户注册
   ↓
自动创建 Tenant「{user}'s Tenant」      is_default = true
   ↓
自动创建 Organization「{user}'s Org」    is_default = true
   ↓
自动创建 Product「Default Product」      is_default = true
   ↓
自动创建 Workspace「Default」            is_default = true
   ↓
用户只看到：[ + 新建项目 ]
```

规则：
- 每层加 `is_default BOOLEAN`，默认层在 UI 中**不渲染面包屑**
- 仅当某层出现第 2 个实例时，该层才在 UI 中显现（渐进式暴露）
- 文档⑨ 的三个免费工具（PRD 整理 / 项目估价 / 变更影响）走**匿名 Tenant**，`Save to good7ob` 时才把匿名 Tenant 转正

> 没有这一条，D2 的五层会直接扼杀文档⑨ 的获客漏斗。**它是 D2 的必要配套，不是可选优化。**

### 3.2 数据隔离：不要逐层 join

五层不意味着每张表都要带五个外键。约定：

```text
每张业务表携带：
  tenant_id       ← 隔离/鉴权的统一入口，所有查询的第一个 where 条件
  <直接父级>_id    ← 结构关系
```

不携带中间层 id。需要跨层统计时走物化视图或汇总表，不要在热路径上串五级 join。

## 4. 其余七项决策

### 4.1 `Requirement` 撞名 → 改 RP，不改 Requirement

冲突：文档①/⑩ 的 `Requirement` = 需求池条目（上游）；文档④ 的 `Requirement Point` = 最细业务规则（下游）。同一个词横跨模型两端。

**决策：保留上游 `Requirement`，把 RP 重新展开为 `Rule Point`（规则点）。**

- `forge_requirement` 三张表 + 6 个 MCP 工具（`create_requirement` / `transition_requirement` / …）已上线，改名要动公开 API
- RP 还没写一行代码，改名零成本
- `FE / FP / RP` 的缩写对称完整保留

```text
Feature（FE）        产品功能
Function Point（FP） 功能点   ★ 唯一估算单位
Rule Point（RP）     规则点   ★ 唯一验收单位
```

### 4.2 Story 废弃（D1，已拍板）

Story 的定义（可独立估算、开发、验收）与 FP **完全重合**。两个估算单位共存 = 必然漂移。
Story 从未落地，直接删除，文档① 的 `Epic → PRD → Story → Task` 相应修正。

### 4.3 Epic 不建表，用 `parent_id`

`forge_requirement.parent_id` 的列注释已写明"用于 Epic 聚合；顶层为 NULL"。
Epic 就是一条有子需求的 Requirement。不要再建 `epic` 表。

### 4.4 人类 Task 与 Agent Task 同表

V33 把 Hermes 的执行计划、状态日志、评估缓存**全部挂在 `pm_tasks` 上**，这个决定已经做了。

```sql
ALTER TABLE pm_tasks
  ADD COLUMN executor_type     VARCHAR(16) NOT NULL DEFAULT 'HUMAN',  -- HUMAN | AGENT
  ADD COLUMN agent_id          BIGINT,
  ADD COLUMN function_point_id BIGINT,        -- 连接产品轴
  ADD COLUMN estimated_hours   NUMERIC(8,2),
  ADD COLUMN actual_hours      NUMERIC(8,2);
```

进度、成本、Token 必须能在**一处**汇总人和 AI——文档⑨ 场景四要的
`Human 14h / AI Agent 3h / Token 1.2M` 只有同表才算得出来。

#### Task 状态机（D5，已拍板：6 态）

文档⑥ 提出 6 正常态 + 5 异常态 = 11 态。压缩到 6 态：

```text
backlog ──► todo ──► running ──► review ──► done
              ▲        │  ▲         │
              │        ▼  │         │
              └──── blocked ◄───────┘
```

| 状态 | 含义 | 吸收了文档⑥ 的 |
|---|---|---|
| `backlog` | 未排期 | BACKLOG |
| `todo` | 已排期待开始 | TODO + **READY** |
| `running` | 人在做 / Agent 在跑 | RUNNING + WAITING_AGENT |
| `review` | 待审核 / 待人工确认 | REVIEW + WAITING_HUMAN |
| `done` | 已完成 | DONE |
| `blocked` | 受阻，需人工介入 | BLOCKED |

**被砍掉的四个，各有去处——不是丢弃，是归位：**

| 文档⑥ 状态 | 去处 | 理由 |
|---|---|---|
| `READY` | 并入 `todo` | READY 与 TODO 的差别只是"依赖是否满足"，而依赖已在 `pm_task_dependencies` 里，**可计算得出**。派生状态不该占状态位 |
| `FAILED` | → `task_execution.status` | **执行失败 ≠ 任务失败**。文档⑥ §9 自己的例子里 Task 执行了 3 次（FAILED / TEST FAILED / SUCCESS），失败属于 Execution。Task 只是回到 `blocked` 或 `todo` 等待重试 |
| `CANCELLED` | → `is_deleted` + `cancel_reason` | 取消的任务不该出现在任何看板和统计里，逻辑删除正是这个语义。而 `blocked` 的任务必须保持可见 |
| `WAITING_HUMAN` / `WAITING_AGENT` | 并入 `review` / `running` | "等谁"是 `executor_type` + `assignee` 已经回答的问题，不需要再占状态位 |

> ⚠️ `pm_tasks` 现有 check 约束只允许 `not_started / in_progress / completed` 三态，
> **必须先放宽**，否则写入会被 check constraint 直接拒绝。存量映射：
> `not_started → todo`、`in_progress → running`、`completed → done`。

### 4.5 缺陷统一叫 Bug

`project_bug` 已上线。文档⑩ 里的 `Issue` 全部改为 `Bug`。
不引入 GitHub 式的泛化 `Issue`——`pm_tasks` 已承担"待办"语义，再来一个 Issue 会三方混淆。

### 4.6 Acceptance Criteria 并入 RP，不单独建表

文档④ 自己给 RP 的定义是：

> RP 应尽量满足：可以明确判断"满足"或"不满足"。

**这就是验收标准的定义。** 在 RP 与 TestCase 之间再插一层 AC 是纯冗余。
做法：`rule_point` 上加三个可选字段承载 Given/When/Then。

```text
rule_point
├── statement   "同一 Tenant 内 Email 必须唯一"      （必填）
├── given       "Tenant A 已存在 user@example.com"  （选填）
├── when        "管理员再次创建同一 Email"            （选填）
└── then        "系统拒绝创建"                       （选填）
```

链路从 `RP → AC → TestCase` 简化为 `RP → TestCase`（N:M），少一张表、少一次同步。

### 4.7 PRD 不是层级节点，是挂在 Requirement 上的版本化文档 ⚠️ 最重要

整套模型里**最容易踩、代价最大**的一个坑。

若把 PRD 设计成 `Requirement → PRD → FE → FP → RP` 的层级节点：

```text
PRD v1.2  →  FE-001 → FP-003 → RP-006
PRD v1.3  →  ？
```

PRD 每升一版，子节点要么被复制（ID 变了，历史断裂），要么被重新挂载（父子失效）。
**而文档④⑤⑨ 的核心卖点"需求变更影响分析"，恰恰要求 FE/FP/RP 跨 PRD 版本保持同一身份**——
只有 RP-006 在 v1.2 和 v1.3 里是同一条记录，才能算出"RP-006 被修改了"。

正确做法：

```text
Requirement (REQ-1024)
├── PRD Document v1.2 ──┐
├── PRD Document v1.3 ──┼── source_ref ──► FE-001 → FP-003 → RP-006
└── ChangeRequest CR-23 ┘                              ▲
                                                       │
                        PRD 是"输入证据"，不是"父节点" ──┘
```

`source_ref` 记录该 FE/FP/RP 来自哪份 PRD 的哪一段——这正是文档⑤ 从 SEERai 学到的
`Source → Sizing Result → Traceability`，也是 AI 能回答"为什么生成这个 FP"的前提。
复用现有 `forge_prd_documents`，不新建表。

### 4.8 Platform 是属性，不是层级（解决文档⑪）

文档⑪ 想引入 `Product → App / Web / Admin` 这一层。不需要——`org_products` 已存在，
而 `App / Web / Admin` **不是 Product，是 Platform**：一个 Product 同时交付到三个端。

```text
org_products              Product  = 产品（good7ob）
  └── screen.platform     Platform = 交付端（app / web / admin / common）枚举
      └── resource.platform
```

⑪ 的整套 Resource 模型直接挂 `product_id + platform`，不新增层级。

### 4.9 Runtime 挂 Workspace，且是本产品的一部分（D6）

D2 把 Workspace 定为"一组项目共享什么"，Runtime 正好是最典型的共享物：

```text
Workspace
├── ai_runtime          ← 1 Workspace = 1 台 Hermes EC2（文档⑧ V1 方案）
│   ├── runtime_lock
│   ├── runtime_event
│   └── runtime_usage   ← 用量向上汇总到 Tenant
├── git_repo_binding
└── agent_config / skill_set
```

Runtime 成本直接复用已上线的 `infra_cost_*` 体系（`infra_cost_record` / `infra_budget` / `infra_bill`），不另起炉灶。

#### D6 的三个连带影响

**① 账单是一张，不是两张。**
文档⑧ §19 的公式 `月费用 = Subscription + Compute + Storage + AI Token` 仍然成立，
但这是**同一张账单的几个 line item**，不是两个产品各开一张。
定价上 Compute 应打包进套餐（如 Standard 含 X 小时/月，超出按量），
而不是让用户产生"我在额外租一台服务器"的感知。

**② 用户不该看到 EC2 / Instance / Runtime 这些词。**
文档⑧ §1 已经说了"不建议定义成出租 EC2"。D6 让这一点更进一步：
连 `Runtime` 这个词都不必暴露给用户。用户的心智模型只有——

```text
创建任务 → 任务在跑 → 任务完成
```

启动、健康检查、空闲停机全部对用户不可见。文档⑧ §12 的 AI Worker 页面
（Status / Instance / CPU / Memory / AWS Cost）**降级为平台运营后台**，不是租户功能。

**③ ⚠️ 自动启停的性质变了——从"省用户的钱"变成"省我们的钱"。**

这是 D6 最容易被忽略的影响：

| | Runtime 独立计费（未采用） | Runtime 属于本产品（D6） |
|---|---|---|
| 空闲停机省的是 | 用户的钱 | **good7ob 自己的毛利** |
| `idle_timeout` 该由谁定 | 用户 | **平台** |
| 用户能关掉自动停机吗 | 能，他自己付费 | **不能，关掉等于直接吃我们的毛利** |

因此文档⑧ §11 把 `auto_stop_enabled` / `idle_timeout_minutes` 设计成**租户可配置字段**，
在 D6 下是错的——它们应当是**平台侧参数**，租户不可见、不可关闭。

对应地，`runtime_usage` 的角色也变了：它不再是"给用户开账单的依据"，
而是 **COGS（销售成本）计量**。毛利公式落在 Tenant 层：

```text
Tenant Gross Margin = Tenant Revenue − AWS Cost − LLM Cost
```

这意味着 Runtime 的压榨效率（预热池、Spot、共享 Worker Pool、Ephemeral Runtime，
即文档⑧ V3 的全部内容）**直接等于毛利率**，优先级应该高于它在文档⑧ 里被排的 V3。

### 4.10 Secret 挂 Organization（D4）

```text
organizations
└── org_secret          ← Git Token / LLM API Key / SSH Key / Cloud Credential
```

配套三条约束（来自文档⑥ §20、⑧ §16）：

1. **密文存储**，复用已上线的 AES-256-GCM 加密方案（`forge_api_keys` 同款）
2. **Agent 永不接触明文**——Runtime 启动时由平台按需注入环境变量，Agent 只能使用不能读取
3. **每次注入写审计**——落 `org_audit_log`，记录 `who / when / which secret / which runtime / which task`

#### D4 的连带影响：环境隔离靠开 Organization，不靠开 Workspace

Secret 在 Organization 意味着**同一个 Organization 下的所有 Workspace 共享同一套凭证**。
如果客户需要 dev / prod 凭证分离，正确做法是在**同一个 Tenant 下开两个 Organization**：

```text
Tenant「Acme」                    ← 一份合同、一张账单、一个配额池
├── Organization「Acme Dev」
│   ├── org_secret: dev 凭证
│   └── Product → Workspace → Project
└── Organization「Acme Prod」
    ├── org_secret: prod 凭证      ← 与 dev 完全隔离
    └── Product → Workspace → Project
```

D3（Tenant = 签约主体，可含多个 Org）恰好让这条路走得通——
不需要为凭证隔离再往 Workspace 加一层 Secret。

## 5. 最终统一模型

```text
tenant                                 ★ 签约 / 计费 / 配额 / 隔离的唯一边界
├── tenant_subscription
├── tenant_quota                       ← 文档⑧ 的 tenant_quota 落在这里
├── tenant_usage                       ← Token / Compute / Storage 汇总
│
└── organizations (tenant_id)          ★ 人与权
    ├── org_members / roles / permissions
    ├── org_audit_log
    ├── org_secret                     ← Git Token / LLM Key / SSH Key
    │
    └── org_products                   ═══ 产品轴（长期，永不归档）═══
        │
        ├── forge_requirement (REQ)    ← 需求池；parent_id 自聚合为 Epic
        │   ├── forge_requirement_version
        │   ├── forge_prd_document     ← 版本化文档（非层级节点）
        │   └── change_request (CR)
        │
        ├── forge_feature (FE)
        │   └── forge_function_point (FP)   ★ 唯一估算单位 · 双轴连接点
        │       ├── fp_estimate / fp_actual
        │       ├── fp_source_ref → PRD 段落  ★ 追溯锚点
        │       └── forge_rule_point (RP)    ★ 唯一验收单位（内含 Given/When/Then）
        │           └── test_case (N:M)
        │

        │

        │
        └── workspace                  ═══ 交付轴 ═══
            ├── ai_runtime → runtime_lock / runtime_event / runtime_usage
            ├── git_repo_binding
            ├── agent_config / skill_set
            │
            └── pm_projects (workspace_id, product_id, organization_id)
                ├── pm_execution_plan                   ← 执行计划，见 04
                │   └── pm_execution_plan_item (→ Task) ← task 链
                ├── project_function_point (N:M → FP)   ← 项目范围

                │   ├── task_execution (runtime_id, token, cost)
                │   │   └── execution_step
                │   ├── pm_task_dependencies
                │   └── pm_task_deliverable
                ├── project_bug
                ├── release
                │   ├── test_plan → test_run → test_run_case
                │   └── quality_gate
                └── forge_ai_work_record
```

### 六条"唯一"原则

| 原则 | 载体 |
|---|---|
| 唯一**估算**单位 | Function Point（不是 Story、不是 Task、不是 Feature） |
| 唯一**验收**单位 | Rule Point（AC 已并入） |
| 唯一**执行**单位 | Task（人和 Agent 同表） |
| 唯一**计费/配额**边界 | Tenant |
| 唯一**权限**边界 | Organization |
| 唯一**追溯**锚点 | PRD 段落 → `fp_source_ref` |
